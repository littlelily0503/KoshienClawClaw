# 2026 夏之甲子園 賽程籤表

第108回全国高等学校野球選手権大会 的籤表、賽程與每日賽果。

## 檔案

| 檔案 | 說明 |
|---|---|
| `index.html` | 網頁本體。籤表結構、賽程、樣式全部在這裡，可單獨開啟 |
| `fetch_results.py` | 從 スポーツナビ 抓賽果，產生 `results.json` |
| `results.json` | 賽果資料（給 http server 用） |
| `results.js` | 同內容，包成 `window.KOSHIEN_RESULTS`。直接雙擊 index.html 也讀得到 |
| `.github/workflows/update-results.yml` | 台灣 07:00–23:00，每 30 分鐘觸發一趟、趟內每 10 分鐘抓一次 |
| `run_tests.py` | 更新機制的回歸測試，`python3 run_tests.py` 一次跑完 |
| `TESTING.md` | 測試矩陣：測哪些項目、為什麼 |

## 建置順序

> Windows 使用者請把以下指令的 `python3` 一律改成 `python`。
> Windows 的 `python3.exe` 是 Microsoft Store 的殼層，執行後不做任何事就結束。
> 若 `python --version` 會跳出 Store，去「設定 → 應用程式 → 應用程式執行別名」
> 把 `python.exe` / `python3.exe` 兩個開關關掉。

### 1. 本機驗證抓取

```bash
pip install requests beautifulsoup4
python3 fetch_results.py --dry-run
```

確認 stderr 印出「解析 48 場，其中 N 場已完賽」。

### 2. 本機驗證前端

```bash
python3 fetch_results.py     # 產生 results.json 與 results.js
```

**直接用瀏覽器開啟 `index.html` 即可**，不需要架 server。
`results.js` 是用 `<script>` 標籤載入的，不受 `file://` 的 CORS 限制。

若要模擬正式環境（讓網頁走 `results.json`）再架 server：

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

正常啟動會印出 `Serving HTTP on 127.0.0.1 port 8000 ...` 並**停住不回提示字元**。
若指令秒回、或瀏覽器顯示 `ERR_CONNECTION_REFUSED`，代表 server 根本沒起來
（最常見原因就是上面那個 `python3` 別名問題）。

檢查重點：已完賽的隊伍有沒有正確晉級到下一輪。若 console 出現
`校名對不上`，代表 Yahoo 的校名寫法與籤表不同，去 `index.html` 的
`NORM()` 補一條替換規則。

### 3. 推上 GitHub Pages

```bash
git init && git add . && git commit -m "init"
git branch -M main
git remote add origin git@github.com:<帳號>/koshien2026.git
git push -u origin main
```

Settings → Pages → Source 選 `main` / `(root)`。

### 4. 開自動更新

Actions 頁面 → 「更新賽果」→ Run workflow 手動跑一次，確認會 commit。
之後每天台灣時間 07:00–23:00 每 30 分鐘自動觸發一趟。

## 兩個更新頻率，不要搞混

```
Yahoo ──(A) 10 分鐘 ──> GitHub Actions ──> results.json ──(B) 5 分鐘 ──> 瀏覽器
```

**(A) 爬蟲頻率**：GitHub 去 Yahoo 抓資料、更新 `results.json`。

**不要用 `*/10` 這種高頻 cron，也不要用整點。** 免費方案的排程工作會被大量丟棄，
實測 `*/10` 設定下一小時往往只跑到一兩趟。GitHub 官方說明只寫「可能因平台
負載延遲或不執行」，沒有保證。

兩個實務上有效的做法：
* **避開 `:00`。** 全世界的 cron 都擠在整點，那是負載最高、最容易被丟棄的一分鐘。
  改用 `:07` / `:37` 這種冷門分鐘，命中率明顯較高。
* **每小時給兩次機會。** 單一觸發被丟掉就等於整整一小時沒更新；半小時一次
  可以把最壞情況砍半。若前一趟還在跑，`cancel-in-progress` 會直接取代它並
  立即重抓，不會漏。

現行做法是**每小時只請 GitHub 觸發一趟**（整點單趟的成功率高很多），
job 進去後自己迴圈，每 `INTERVAL` 秒抓一次，跑滿 `RUN_SECONDS` 秒後收工，
下一個整點由新的一趟接手（`cancel-in-progress: true` 會直接取代前一趟）。

迴圈每趟開頭都做 `git fetch` + `git reset --hard origin/main`。
`results.json` / `results.js` 是 bot 完整重新產生的檔案，不需要合併，
用 reset 而非 rebase 可以徹底避免衝突與 rebase 中斷。你在網頁編輯器改的
`index.html` 不受影響，reset 的是 bot 自己的工作區、不會覆蓋遠端歷史。
推送若被拒（剛好撞上你的 commit），只印訊息、下一趟重抓重試，不會中斷整趟。

要改時段，動 `cron` 的小時欄位（UTC，台灣時間 = UTC + 8）：

| 需求 | cron |
|---|---|
| 台灣 07:00–23:00（目前） | `7,37 23,0-15 * 8 *` |
| 台灣 09:00–23:00 | `0 1-15 * 8 *` |

要改趟內頻率，動 workflow 最上方的 `env`：

```yaml
env:
  RUN_SECONDS: 3000   # 這一趟總共跑多久（秒）
  INTERVAL: 600       # 每次抓取的間隔（秒）
```

`RUN_SECONDS` 應略長於觸發間隔，讓每趟剛好銜接到下一趟；也不要超過
`timeout-minutes` 換算的秒數。目前 2100 秒配 600 秒間隔 = 每趟抓 4 次、
歷時 30 分鐘，與 30 分鐘的觸發間隔相接。

公開 repo 的 Actions 分鐘數不計費，所以長時間 sleep 沒有成本問題。

**(B) 網頁重讀頻率**：開著的分頁去自己的網站重讀 `results.json`，
**完全不碰 Yahoo**，只是省下手動 F5。改 `index.html` 的 `REFRESH_MS`。
僅在分頁可見、且當天有比賽時才運作。

B 刻意設得比 A 短：B 不知道 A 何時更新，設短一點才能保證 A 一更新、
最多 5 分鐘內就看得到。兩者不衝突。

`fetch_results.py` 裡沒有任何頻率設定，它只負責「抓一次」；
裡面的 `timeout=20` 是單次 HTTP 請求逾時，與頻率無關。

## 手動更新

爬蟲掛掉時，直接改 `results.json` 就行（`results.js` 是同一份內容包一層賦值）：

```json
"r1-1": { "teams": ["札幌日大", "仙台育英"], "score": [1, 3], "status": "試合終了" }
```

`teams` 的順序不重要，前端會依校名對齊——實測 Yahoo 的排列時而勝隊在前
（仙台育英 3-1 札幌日大）、時而敗隊在前（聖隷 0-1 佐野日大），不能靠位置判斷。

載入優先序是 `results.js` → `results.json` → `index.html` 內建。兩個檔案
都刪掉則退回內建籤表，頁面仍可正常顯示。

用 PowerShell 檢視檔案內容要加編碼參數，否則日文校名會顯示成亂碼
（只是顯示問題，檔案本身沒壞）：

```powershell
Get-Content results.json -Encoding UTF8 -TotalCount 15
```

## 版面

視窗寬度 760px 以下自動切換成窄螢幕版型，斷點在 `index.html` 的 `NARROW_AT`：

- **分區籤表**不畫連接線，改為同一分區內依 1回戰 → 2回戰 → 3回戰 縱向排列。
  橫向樹狀圖在手機直式螢幕上每欄只剩約 120px，長校名必然被截斷。
- **完整賽程**不用表格，改為日期標題 + 比賽卡片，與分區籤表同一套版型
  （客隊在上、主隊在下、比分靠右）。六欄表格在 390px 上會把校名擠成直排。
  注意：`.node` 預設是 `position:absolute`（籤表靠 JS 算座標），
  任何把 `.node` 放進文件流的新版型都必須自行覆寫 `position:static`，
  否則卡片會全部疊在同一個原點。
- **八強籤表**改為清單。八強四場全部完賽後，順序自動翻轉成
  決賽 → 四強賽 → 八強賽，把還沒打的擺前面。

|---|---|---|

**手動改完只要 commit 該檔案即可**，不需要重推整包。
但注意：`results.json` / `results.js` 由 bot 自動 commit，
若你在本機也跑過 `fetch_results.py`，本機版本會和遠端衝突。
最省事的做法是**手動修改一律用 GitHub 網頁編輯**（檔案頁面右上角的鉛筆圖示），
就不會有本機與遠端不同步的問題。

## 順延與中止

スポーツナビ 處理順延的方式是：**原列保留並改標「試合中止」，另外新增一列重賽**，
而且重賽列的 `gid` 會跳號（實測 8/12 東海大甲府－健大高崎，原列 `2021048506`，
8/13 的重賽列是 `2021048619`）。同日其他場次的開賽時刻也會跟著往前挪。

因此 `(日期, 時刻)` 和 `gid` 都不是穩定主鍵。目前的對應鍵是
**輪次 + 對戰組合**，這在單淘汰賽制下唯一且不受改期影響：

1. 雙方都已確定 → 比對輪次與兩隊校名（不分先後）。同組合出現兩列時取有比分的那列。
2. 只有一邊確定（上一輪中止或未打完）→ 比對該隊是否出現在該輪的某一列。
3. 兩邊都未定（尚未抽籤）→ 退回原定日期時刻。
4. 再不行 → 退回原始 `gid`。

**比分方向**同樣只需要一邊的隊名就能定向。兩邊都無法對應時**不套用比分**——
方向不明的比分會導致勝隊判錯，而錯誤會沿著籤表一路往下傳，留空遠比給錯安全。
（2026/8/16 實際踩過：`r2-10` 中止未重賽時，`r3-5` 的比分被原封不動套用，
把 4 給了實際 1 比 4 落敗的佐野日大。）

對應成功後，網頁上的日期、時刻、大會日、box 連結全部改用 Yahoo 的實際值，
賽程也依實際日期時刻重新排序，原定的休養日若被排入比賽會自動不再標示為休養日。
換日者標「順延」，同日內時刻微調不標。中止未重賽的場次標「中止」且**不會晉級**
（`decided()` 要求狀態含「試合終了」），避免把未打完的比賽誤判為結果。

`fetch_results.py` 不做任何對應，只照實吐出 Yahoo 表格的每一列；
對應邏輯全在 `index.html`，因為前端本來就有逐輪解析勝隊的機制。

## 資料新鮮度

GitHub 的排程一定會被丟棄一部分，無法保證每趟都觸發。因此網頁本身會檢查
`updated` 時間：大會期間若超過 90 分鐘沒更新，頁首會出現紅色警示列。
**看到警示列就表示畫面上的比分可能是舊的**，重新整理或到 Actions 手動
Run workflow 一次即可。門檻在 `index.html` 的 `renderStale()`。

## 八強抽籤

**不需要手動填。** 八強與四強的配對是賽後現場抽籤決定的，籤表上沒有結構可循，
但 スポーツナビ 公布後會把隊名寫進該列，程式直接採用（`linkFromTeams()`）。

處理順序是：先試著反推「這隊是從哪一場打上來的」把來源接起來；接不上時
（上游分區未解析、校名寫法不同等）**直接採用 Yahoo 給的隊名**，縣名由籤表
原有的 49 校資料補回。八強以後是重新抽籤，來源自哪一分區不影響任何顯示，
沒有理由因為接不上來源就整組空白。

若 Yahoo 遲遲未更新而你已從新聞得知配對，可以手動填 `index.html` 的 `DRAW`
覆寫，格式是「來源場次編號」：

```js
const DRAW = {
  qf1:{a:"r3-1", b:"r3-3"}, qf2:{a:"r3-4", b:"r3-2"},
  qf3:{a:"r3-7", b:"r3-8"}, qf4:{a:"r3-6", b:"r3-5"},
  sf1:null, sf2:null
};
```

手動值優先於自動接線。Yahoo 公布後可以改回 `null`，兩者結果應一致。

## 注意

- `gid`（スポーツナビ 場次編號）是連號的，`index.html` 由 `2021048480`
  依出賽順序自動推算，不需維護。若朝日改制導致連號中斷，在 `DATA`
  個別填 `gid:"..."` 覆蓋。
- 抓取對象是他人網站。目前每天約 85 次、每次一頁，整屆大會約 1,500 次請求。
  以單一頁面計算仍屬極小的量，但不建議把 (A) 再往下壓，也不要平行化。
  GitHub Pages 每小時的建置次數有軟性上限（約 10 次），10 分鐘一次是 6 次／小時，
  剛好在界內；壓到 5 分鐘就是 12 次／小時，Pages 反而來不及重建。
  這個限制只適用於 (A)，(B) 不受影響。
- **先攻後攻**：スポーツナビ 一律「後攻 － 先攻」排列，前端據此反轉成國際慣例
  （客隊在上、主隊在下）。此資訊在比賽開打後才出現，賽前維持籤表順序。
- **進行中的比分不會晉級**：`decided()` 要求 `status` 含「試合終了」，
  所以 5 回領先 1-0 只會顯示比分與紅色 LIVE 標記，不會把隊伍送進下一輪。
- 雨天順延會讓日期與時刻改變，`ORDER` 的 (日期, 時刻) 主鍵會對不上，
  屆時 stderr 會印出 `對不到賽程表的列`，手動修 `ORDER` 即可。
